# Verification notes: UTP-20261115-01 (eMudhra one-byte CA keys)
Checked 2026-11-15.

| Claim | Source | Evidence |
|---|---|---|
| Eight eMudhra intermediate CA keys compromised; six issue TLS certificates | [Apple 149555](https://support.apple.com/en-us/149555) | "The private keys of eight intermediate CAs operated by eMudhra were compromised." Two code-signing, six TLS. Published Date: November 09, 2026. |
| With them, someone could make certificates valid-looking for any site | Apple 149555 | "Someone with keys from these six CAs could create certificates that appear valid for any website." |
| Each private key was effectively one byte; cracked in milliseconds | [Scott Helme](https://scotthelme.co.uk/eight-bits-of-trust-emudhras-ca-keys-cracked-in-milliseconds/) | P-384 keys, "inherently weak single-byte keys"; the arrangement "rested on eight bits"; recoverable "in milliseconds on commodity hardware". 2026-10-20. |
| "256 possible values" | arithmetic on Helme's "single byte" | One byte = 2^8 = 256 values (Helme notes this too). MacRumors' phrasing "private key values below 256" matches. |
| Anyone could recover them; reported 17 Oct | [we-have-a-problem](https://emudhra.we-have-a-problem.com/) | "incorrectly generated by the CA. This means that anyone can recover them from the certificates." Reporter "Wayne" signed a message with all eight keys and reported to root programs on 17 October. |
| Chrome and Firefox blocked the same day; Microsoft 20 Oct; Apple 22 Oct | we-have-a-problem timeline; Helme | Timeline: 17 Oct Firefox and Chrome blocked; 20 Oct Microsoft platforms; 22 Oct Apple. Helme: Chrome CRLSet that evening, Mozilla OneCRL a few hours later. |
| Test page: error = protected | we-have-a-problem | Test hosts such as `dv-g3b-emudhra.we-have-a-problem.com`; "A ✅ only means that the connection failed"; a certificate error means the client does not trust the compromised intermediates. |
| Safari covered; curl and git trusted them until macOS 27.2.1; 26.7.3 and 15.8.3 for older | Apple 149555 | Safari, Mail and apps using Apple frameworks blocked via automatic configuration updates; "Starting in macOS 27.2.1, these command-line tools stop accepting these certificates"; also 26.7.3 and 15.8.3. |
| macOS 27.2.1 out November 9 | [Apple security releases](https://support.apple.com/en-us/100100) | macOS Golden Gate 27.2.1, Tahoe 26.7.3, Sequoia 15.8.3: 09 Nov 2026. (The test site's timeline says 10 Nov; Apple's date wins, likely a time-zone difference.) |
| Electron apps need their own update | we-have-a-problem | "Electron apps only pick up Electron's fix once they are updated to a version built on a patched Electron release." Patched: 44.9.1, 43.8.1, 42.11.16. |
| Certificates valid until 2039 | Helme | Devices that can't be updated remain exposed "until the certificates expire in July 2039". Only one source; said as "until 2039". |
| eMudhra exits the business; says no breach | [eMudhra press release](https://emudhra.com/en/press-release/emudhra-to-exit-global-ssl-tls-certificate-business) | 2026-10-22; "Its infrastructure was not compromised and no data was breached." Not in the VO; in Producer notes only. |

Disagreement noted: eMudhra's release says nothing about the keys being weak and blames "social media amplification"; the disclosure site and Helme say the keys were generated incorrectly. The script states only what the root programs and Apple say.
Not claimed: any use of the keys in a real attack; an iOS fix; specific Android versions; Windows versions.
Buzz: HN 1,281 pts "eMudhra intermediate CA compromise" (2026-10-20), 1,202 pts "Apple's git still trusts the compromised eMudhra certificates" (2026-10-28), 1,157 pts eMudhra exit (2026-10-22), 957 pts Helme (2026-10-21); r/apple top-of-week "macOS 27.2.1 Fixes eMudhra Certificate Flaw" (MacRumors, 2026-11-09).
